# Problem Reports

## Flow

1. The host and extension record bounded, local mount lifecycle events in their existing App Group. No remote logger or SDK starts at launch.
2. Open **Help > Report a Problem**, the diagnostics sheet, or a failed mount sheet. Enter a description, optional reproduction steps and optional reply email.
3. Create a snapshot, review the exact JSON, then export it locally or explicitly consent and send it. Editing invalidates the snapshot and consent. Upload failures leave the same report available for export; there is no background queue or automatic retry.

The recorder deliberately excludes labels, paths, volume UUIDs, serial numbers, contents, and arbitrary NSError text/userInfo. Error domains/codes and a bounded underlying-error chain are retained, including the original Disk Arbitration status before the UI converts it to a friendly message. BSD identifiers are temporary and can be reused: a historical event does not prove the same physical device is currently connected. Process/attempt IDs are random, not persistent user IDs.

The shared history retains at most 400 events, 512 KiB, and seven days (pruned on the next read/write). Per-process pending work is bounded. Storage failures and dropped events are exposed in the snapshot. An absent extension event is not proof that the extension was never invoked: an older extension, a crash before asynchronous persistence, or unavailable App Group storage can leave gaps. This is not a replacement for a full system trace or a crash reporter.

On macOS 15, FSClient's unsupported third-party registration query remains unknown; the report must not turn that into a disabled/not-installed conclusion. Current state is captured separately from timestamped history. File I/O logging is not enabled and no new disk writes, mounts or enablement changes are performed to prepare a report.

## Configure Sentry

The host target's Debug and Release configurations include the maintainer-provided public HTTPS DSN for project `4512345930924032` in organization `huanchuantech` (US ingestion). `Config/xntfs-Info.plist` expands the `XNTFS_SENTRY_DSN` build setting into the final `XNTFSSentryDSN` key; the remaining app metadata is generated by Xcode. A custom `INFOPLIST_KEY_XNTFSSentryDSN` setting alone was not emitted by Xcode 27.1, so verify the built plist rather than just the build settings. Forks should replace `XNTFS_SENTRY_DSN` with their own project's public DSN or set it to an empty string to disable sending. Do not put an API token, account password, or a DSN secret in the app. The extension has neither this DSN setting nor a network entitlement; only the host has outbound network access.

The host uses Foundation URLSession and Sentry's documented Envelope ingestion endpoint, with one `feedback` item and one JSON attachment. It does not use the deprecated user-feedback REST endpoint and does not upload each local log as an error event. HTTPS, explicit consent, a 512 KiB report limit, ephemeral networking, no cookies/credentials, no redirects, timeouts and receipt-ID checks apply. A successful response means HTTP acceptance, not that Sentry retained every item or that a human read it. Quotas/filtering may still drop data, so keep local export available.

Before shipping a configured build:

- Use a synthetic report to verify appearance in **User Feedback** and download/compare the attachment, including Chinese text. A matching ingestion receipt alone does not verify the dashboard or attachment retention; those checks require signed-in project access.
- Check quota, attachment availability, privacy/retention settings and who can access the project. The free Developer plan currently includes 1 GB attachments; user feedback itself does not consume error quota. Quotas are organization-wide, not per installed app.
- Update App Store Connect privacy answers and review notes for optional diagnostics, user content and contact details. User consent alone does not automatically exempt the app from privacy disclosures; check Apple's criteria and actual receiver behavior.
- Verify the signed host and extension can share the recorder on supported macOS versions. An unsigned CLI test proves the store/transport logic, not FSKit process permissions on a user's Mac.

## Verification

Run `bash tests/run_problem_reports.sh` for isolated recording, retention, privacy filtering, report serialization, envelope framing, consent and mocked transport tests. These tests make no external requests and mount no disks. `tests/run_volume_regressions.sh` includes the shared recorder when compiling the extension regression harness.
